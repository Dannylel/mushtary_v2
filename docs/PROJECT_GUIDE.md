# Mushtarry MVP - Complete Project Guide

## Purpose

Mushtarry is a local-first procurement intelligence MVP. It demonstrates how AI can help a buyer create a structured RFP, assess tender quality, validate a vendor registration, identify appropriate vendors, compare submitted proposals, and retain an auditable buyer decision.

The governing product rule is:

```text
AI generates or recommends -> buyer reviews -> buyer approves -> system action occurs
```

AI never makes a binding award. A tender generated by the draft flow is private until the Buyer-Admin approves it. Approval is the only action that publishes it into the vendor tender feed.

## Running the demo

From the project root:

```powershell
uv run python api.py
```

Open `http://localhost:8000`. The application uses a local Ollama-compatible model configuration from `.env`/`agents/llm_config.py`; it does not send tender data to a hosted model by default.

## Buyer tender workflow

1. A user signs in as a demo buyer. The backend assigns the buyer profile and tender reference.
2. The buyer enters required tender controls and the Scope of Work.
3. The buyer may run **Evaluate / Rewrite SoW** to obtain a readiness review and a rewritten scope.
4. The buyer may run **Populate Deliverables & Optional Sections**. This creates editable deliverables, timeline milestones, requirements, responsibilities, and evaluation inputs without creating a tender or publishing anything.
5. The buyer generates the tender. The extractor turns the brief into a validated `TenderBuyerForm` and the pipeline drafts four sections in parallel: context, scope, execution, and legal/evaluation.
6. The pipeline assembles the 18-section RFP, runs Tender Health review, and produces JSON and PDF outputs.
7. The draft remains `PENDING_BUYER_APPROVAL`; it is not returned by the vendor feed.
8. The Buyer-Admin selects **Approve & Publish to Vendor Feed**. The approval is persisted and the tender becomes visible to vendors.

## Tender document structure

The generated tender includes:

1. Tender data sheet
2. Introduction and bidder instructions
3. Award and contract rules
4. Vendor document requirements
5. Proposal packaging and submission controls
6. Project overview, objectives, and scope
7. Deliverables table
8. Timeline and milestones table
9. Team requirements
10. Legal terms, confidentiality, evaluation, payment terms, and annexures
11. Buyer approval/document-control page

Deliverables are represented as structured rows: name, description/acceptance output, format, and deadline. Timeline rows contain phase, milestone, and target timing. Both are rendered as tables in the UI preview and PDF.

## AI drafting and safeguards

The drafting graph fans out into four independent section agents and then assembles the output. Each section has a Pydantic schema and deterministic fallback. Legal drafting retrieves approved clause sources from the local knowledge base and is instructed to write its JSON values in professional English.

The extractor normalizes imperfect local-model output before validation. In particular, a `null` deliverable description is converted into a reviewable placeholder rather than failing the whole extraction.

Guardrails validate structured outputs. A fallback protects the application from malformed model JSON, but a fallback result should be reviewed before publication; it is not proof that a draft is ready for a client-facing tender.

### Consistency and publication gate

Before Tender Health review, the Tender Consistency and Compliance Agent reconciles hard buyer facts and reviews semantic conflicts. Buyer-entered deliverables and milestone dates replace conflicting generated values. The system never invents a Saudization percentage when the buyer supplied only a policy flag. A high-severity consistency finding blocks Buyer-Admin publication until it is resolved.

The agent handles semantic judgment. Deterministic controls handle fixed facts, required rows, publication state, and authorization.

## Tender Health Committee

Tender Health is an internal quality review shown in the web UI. It considers scope clarity, commercial clarity, compliance readiness, vendor participation risk, and aggregate readiness. It can recommend improvements, but it does not independently publish, reject, or award a tender.

## Vendor-side demo workflow

After a Buyer-Admin publishes a tender:

1. A demo vendor signs in.
2. The vendor sees approved tenders in the vendor feed, including buyer BRI/payment signals and tender requirements.
3. The vendor submits a demo proposal with price, delivery timeline, and technical/commercial summaries.
4. The buyer opens Submitted Vendors for an advisory comparison.
5. The committee output is persisted as an AI artifact. The buyer may approve the recommendation, but contract award remains a separate, unimplemented buyer action.

Vendor feed, jobs, sessions, tenders, and proposals are in memory and reset when the server restarts. They are suitable for a controlled demo, not production persistence.

## Reputation intelligence

### Vendor Reputation Index (VRI)

VRI is a 0-100 vendor intelligence score. The demo combines performance rating, compliance, institutional verification, delivery performance, financial strength, tender success, contract history, and AI risk signals. It also exposes category-specific VRI, vendor badges, and special positive badges.

### Buyer Reliability Index (BRI)

BRI is a 0-100 buyer trust signal. The demo combines payment reliability, evaluation fairness, dispute behavior, procurement volume, platform activity, and AI risk signals. Vendor-facing tender cards show the buyer's BRI, badge, payment reliability, and dispute level.

### AI Vendor Selection Engine

Shortlisting combines tender requirement match, technical/proposal quality, commercial competitiveness, VRI, and risk adjustment. It returns high-, medium-, and low-match groups, exclusions, top three recommendations, explainability reasons, and advisory committee signals.

The 30 buyer and 30 vendor profiles are deterministic demo data. They illustrate the scoring model but are not live company, rating, payment, dispute, or verification records.

## Vendor validation

The validation agent follows the intended sequence: CR lookup, duplicate detection, category alignment, and document-completeness check. Its current integrations in `agents/vendor_validation/stubs.py` are demo adapters. They must be replaced with authenticated registry/database/document-validation services before production use.

The Document Applicability Agent now identifies required versus conditional document types from selected categories and uploaded metadata. It is advisory and cannot claim a document is authentic, valid, or current; those checks require issuer, expiry, legal-name, and registry integrations.

Do not interpret a demo validation outcome as official legal or registry verification.

## Persistence and audit

`agents/artifact_store.py` uses SQLite to retain AI artifacts, their input snapshots, structured output, prompt metadata, and buyer approvals. This is the persistent audit trail in the MVP.

The marketplace state is intentionally separate and volatile. Restarting the API clears active jobs, pending drafts, published tenders, and submitted demo proposals but retains persisted AI artifacts.

## API overview

Important endpoints:

| Endpoint | Purpose |
|---|---|
| `POST /api/jobs/draft-guided` | Creates a private tender draft from buyer Scope of Work. |
| `POST /api/jobs/populate-optional-sections` | Derives editable optional fields only. |
| `POST /api/jobs/sow-review` | Reviews/rewrites a Scope of Work. |
| `POST /api/jobs/extract` | Extracts a structured form from an uploaded document. |
| `GET /api/jobs/{job_id}` | Polls background job status/result. |
| `POST /api/artifacts/{artifact_id}/approve` | Records buyer approval and publishes a matching pending tender. |
| `GET /api/tenders/feed` | Returns only approved/published vendor-feed tenders. |
| `POST /api/tenders/{tender_id}/proposals` | Submits a demo vendor proposal. |
| `GET /api/proposals/compare` | Returns buyer-side advisory proposal comparison. |
| `GET /api/reputation` | Returns VRI/BRI marketplace snapshot. |
| `POST /api/intelligence/shortlist` | Runs tender-specific vendor shortlisting. |

## Verification

Run the standard-library test suite:

```powershell
uv run python -m unittest discover -s agents/tests -v
```

The current suite covers prompt registry consistency, guardrail behavior, RAG chunking, and retrieval failure safety. It does not replace a full browser end-to-end test; rehearse the complete buyer-to-vendor flow before a client recording.

## Production boundaries

Before production, implement authenticated user/organization roles, durable tender/proposal storage, real Wathq/registry and document integrations, authorization controls, secure document storage, publication and award workflow states, policy configuration, audit immutability, and independent end-to-end tests. The MVP intentionally exposes local demo behavior rather than claiming those services are already live.
